# Billion-document RAG (distributed search + LLM grounding at frontier scale)

## Bar anchors
- **Mid-level (L4/E4):** Produces a generic RAG pipeline: embedding service → vector DB → LLM. Picks pgvector or "a vector DB" without sizing memory. Defines core endpoints (`POST /search`, `POST /documents`). Knows about chunking but treats it as a fixed-size split (e.g., 500 tokens). Does not need to name a specific ANN algorithm, articulate the multi-stage cascade, or quantify recall-vs-latency unprompted.
- **Senior (L5/E5):** Names HNSW vs DiskANN with the memory/latency tradeoff and explains why pure-RAM HNSW dies above ~100M-1B vectors. Articulates the multi-stage cascade: BM25 / bi-encoder for top-100 candidates → cross-encoder rerank for top-K → LLM grounding. Knows about hybrid (dense + sparse) retrieval and identifies embedding-model versioning as a real operational problem (re-embedding 1B docs is multi-day work). Discusses sharding by-doc-id vs by-cluster. Picks a reranker (Cohere Rerank, ColBERT) and prices it (~80-200ms on top-100).
- **Staff+ (L6/E6+):** Drives the session proactively. Quantifies the RAM-vs-disk wall with the formula (`1.1 × (4d + 8M) × N` bytes for HNSW; ~1.4 TB for 1B vectors at d=128, M=16) and picks an index with explicit criteria (DiskANN at 64GB RAM + SSD for cost; Pinecone slab + compaction for ops simplicity; Turbopuffer S3-first for storage cost at the price of cold-query latency). Allocates the latency budget across stages (Perplexity median 358ms ≈ 100ms retrieve + 120ms rerank + 138ms LLM first-token). Names Anthropic Contextual Retrieval as the chunking-context solution (prepending LLM-generated context summary to each chunk reduces top-20 retrieval failure rate from 5.7% to 1.9% — 67% improvement) and prices it (LLM context generation is cheap given prompt caching). Addresses freshness via append-and-compact (Pinecone slab pattern, Milvus segment compaction) since HNSW has no native delete. Handles filter selectivity for multi-tenant search (naive pre/post filter falls back to brute force under selective filters; in-algorithm filtering like Azure ACORN or per-tenant Curator-style subtree indices is the production answer). Stretch (Sr Staff bar): mentions out-of-distribution detection (similarity-score threshold → "I don't know" path) so the LLM doesn't hallucinate from garbage retrieval; quantifies cost of re-embedding 1B docs (multi-day on a single GPU) and proposes dual-index migration strategy.

## Canonical decomposition

### Requirements
**Functional:**
- User submits a natural-language query; system returns a grounded answer with citations
- Retrieve top-K relevant chunks from a billion-document corpus
- Rerank candidates with a cross-encoder or LLM-judge
- Generate the answer with the LLM using retrieved chunks as context
- Support filtering (per-tenant, per-source, per-date) and role-based access control
- Ingest new documents continuously (news, user uploads) with bounded indexing lag

**Non-functional (with numbers):**
- 1B+ documents indexed (Perplexity reports 200B+ unique URLs on Vespa; 400+ PB hot storage)
- 1M QPS total system load (peak); ~200M queries/day sustained at Perplexity scale (~2,300 QPS sustained)
- ~10K RPS to the LLM grounding component (most queries get a grounded answer; some get a "no result" fast-path)
- p95 retrieval latency <100ms; p99 end-to-end (retrieve + rerank + LLM first-token) <2s; Perplexity median ranking latency 358ms
- Freshness: news / real-time events <1hr indexing lag; static docs <24hr lag; per-collection SLO
- Multi-tenant with role-based access control; selective filters must not collapse to brute force
- Cost: per-query cost in $0.001-0.01 range at frontier scale (vector search + reranker + LLM grounding all priced in)

### Core entities
- **Document:** doc_id, content, source_url, metadata (tenant_id, acl, source, last_modified), last_indexed_ts
- **Chunk:** chunk_id, doc_id, content, context_summary (Anthropic-style 50-100 token prepended summary), embedding, offset, position
- **Query:** query_id, tenant_id, text, query_embedding, filters, top_k
- **Retrieval result:** chunk_id, score, source_doc, retrieval_stage (BM25 / dense / hybrid), rerank_score
- **Citation:** cited_chunk_ids, confidence, position_in_answer

### API
- `POST /v1/search` body={query, filters, top_k, model} → SSE stream of LLM-grounded answer with inline citations
- `POST /v1/documents` body={url | content, metadata, tenant_id} → {doc_id, indexing_status}
- `GET /v1/documents/:id` → {status: indexing | indexed | failed, indexed_ts}
- `DELETE /v1/documents/:id` → soft-delete with tombstone (HNSW can't physically delete; compaction reclaims later)
- `GET /v1/usage` → tenant query / token consumption per period

### HLD
**Query path.** User query hits a stateless **gateway** (auth + tenant context + filter validation). The query is sent in parallel to (a) an **embedding service** (sub-50ms to produce the dense query vector) and (b) a **BM25 index** (lexical retrieval, ~10-20ms for top-N candidates). Both feed the **candidate retrieval stage**: the dense top-N (vector search over the index) and BM25 top-N are merged via Reciprocal Rank Fusion or learned-to-rank into ~100-200 candidates in under ~50ms total. The candidate set is sent to the **reranker stage** (Cohere Rerank ~80ms / ColBERT ~tens of ms on a single GPU / cross-encoder ~120ms) that narrows to top-K (typically 10-20). Top-K chunks plus their content are sent to the **LLM grounding service** which generates the answer with citations as an SSE stream (first-token <500ms thanks to prompt caching of the system prompt). Total latency budget allocation: ~100ms retrieve + ~120ms rerank + ~138ms LLM TTFT = 358ms median (matches Perplexity's published number).

**Ingest path.** New documents arrive via push (`POST /v1/documents`) or pull (web crawler, Kafka stream from upstream system). Each doc is chunked (typical 200-500 tokens with overlap) by a **chunker service**; each chunk goes through a **contextual summary generator** (an LLM call producing a 50-100 token document-context summary that gets prepended to the chunk text before embedding — Anthropic Contextual Retrieval). The chunker output enters two parallel paths: (1) the **embedding service** (batched, GPU-bound, ~50K tokens/sec on an A100) produces dense vectors and writes them to the vector index; (2) the chunk text is also written to the **BM25 index** with the contextual summary prepended. The vector index uses an **append-and-compact** topology: writes go into small fast-built slabs (scalar quantization or random projection), background compaction periodically merges small slabs into large cluster-indexed slabs using the full ANN algorithm (Pinecone slab pattern, Milvus segment compaction). Deletion is a tombstone marker resolved at query time and reclaimed at compaction.

**Index choice.** The catalog dive treats this as a first-class decision with three production-tested options: (a) **DiskANN** — billion vectors on a single 64GB-RAM machine with SSD, >5K QPS, <3ms p50, ~40× cost reduction vs pure-HNSW (reported migration: 3TB RAM HNSW → 96GB DiskANN); (b) **Pinecone slab / Milvus segment** — immutable slabs in object storage, stateless query executors cache slabs on local SSDs, compaction merges over time, LSM-tree pattern applied to ANN; (c) **Turbopuffer** — S3-first storage at $0.02/GB (30× cheaper than 3×-replicated SSD), warm queries 8-10ms, cold queries 500-600ms (cache fill from S3). Pick one with explicit criteria — at 1B+ scale, pure HNSW is not in the option set.

### Deep dives
1. **Index choice and the RAM-vs-disk wall.** Pure HNSW for 1B 128-dim vectors at M=16 requires ~1.4 TB of RAM (formula: `1.1 × (4d + 8M) × N` bytes). DiskANN puts the graph on SSD with 64GB RAM as the working set; reported single-machine numbers are 1B vectors at >5,000 QPS and <3ms mean latency with 95%+ recall@1 (Subramanya et al., NeurIPS 2019). The named technique is Vamana — a graph algorithm co-designed with disk-resident storage (smaller search radius than HNSW to minimize SSD page reads). SPANN extends this with IVF-on-disk (centroids in RAM, posting lists on disk, 2× faster than DiskANN at 90% recall). Pinecone's slab architecture is the cloud-native answer — immutable slabs in S3, stateless query executors that cache slabs on local SSDs, compaction job merges small slabs (built with cheap scalar quantization) into larger slabs (cluster-indexed). The LSM-tree-style append-and-compact pattern sidesteps HNSW's deletion problem entirely. Turbopuffer is the cost-extreme: S3 as source-of-truth at $0.02/GB vs $0.60/GB for 3×-replicated SSDs, accepting 500-600ms cold-query latency in exchange. Staff+ commit: pick one, justify with TCO math (RAM cost + storage cost + recall budget + cold-query latency budget). RaBitQ (SIGMOD 2024) is the 2025+ quantization frontier — 1-bit-per-dimension with provably unbiased distance estimator, 32× compression, 94%+ recall on 768-d vectors; mention it as the per-vector compression complement to dimensional truncation (Matryoshka).

2. **Multi-stage cascade with latency budget allocation.** Generic search ends with the top-K from a single index. RAG requires a cascade: stage 1 (cheap, broad — BM25 or dense bi-encoder) returns top-100 candidates; stage 2 (expensive, narrow — cross-encoder or ColBERT) returns top-K; stage 3 (LLM grounding) consumes the top-K. The latency budget for sub-second p99: ~100ms stage 1, ~120ms stage 2, ~138ms LLM TTFT = 358ms median (Perplexity's published number on Vespa). Reranker choice with prices: Cohere Rerank 4.0 Pro ~200ms (accuracy-tuned), Cohere Rerank 4.0 Fast ~80ms (latency-tuned), ColBERT ~tens of ms on a single GPU but storage cost 10-100× larger than a sentence-embedding index. Hybrid retrieval (dense + sparse) joins at stage 1 via Reciprocal Rank Fusion or learned-to-rank; native support in Weaviate, Qdrant, Turbopuffer, Vespa; Anthropic Contextual Retrieval prepends LLM-generated context summary to chunks before BOTH the dense embedding AND the BM25 indexing for a measured 67% reduction in top-20 retrieval failure rate (5.7% → 1.9%) — and that prepend-with-LLM cost is cheap given prompt caching of the document context (the LLM context-summary call benefits from the same caching that makes the application layer cheap). Staff+ commit: stage budgets, reranker pick + price, when to skip stage 2 (high-confidence stage 1 results), out-of-distribution detection (similarity-score threshold → return "no results" fast-path rather than feeding garbage to the LLM).

3. **Freshness via append-and-compact (no in-place mutation).** HNSW has no native delete operation — production systems use tombstones plus periodic full rebuilds at great cost. For a 1B-vector index, full rebuild is hours-to-days on a GPU. The production answer is to abandon in-place mutation entirely: writes go into small immutable slabs (Pinecone) or segments (Milvus), reads union across all slabs / segments with tombstone resolution at query time, background compaction merges small slabs into larger cluster-indexed slabs. This is the LSM-tree pattern applied to ANN. For news/real-time content, per-collection freshness SLO matters: Bing's framing explicitly distinguishes "a stale fact in grounding is a hallucination, not just a stale ranking" — drives crawl rate and snapshot consistency requirements. Newer techniques (MN-RU, FreshDiskANN for the Vamana family) target in-place streaming updates but are still emerging; production systems as of 2026 are dominated by append-and-compact. Staff+ commit: per-collection freshness SLO, compaction cadence, query-time tombstone resolution policy, anti-pattern naming (don't propose periodic full rebuild on a 1B-vector index — it's hours of GPU time you can't afford).

## Known failure modes
1. **HNSW tombstones accumulating under high churn → recall degradation.** Tombstones can't be removed without rebuilding the graph; as they accumulate, recall drops (the graph traversal visits dead nodes that waste IO/compute). For a corpus with 5% daily churn, recall@K can drop noticeably within weeks. Production answer: append-and-compact topology (Pinecone slab, Milvus segment) where compaction physically removes tombstoned vectors when it merges slabs — eliminates the periodic-full-rebuild operational burden. For an existing HNSW deployment that can't be replaced wholesale, run shadow read traffic against a freshly-rebuilt index, compare recall, swap when ready.

2. **Cross-encoder rerank blowing the latency budget on top-K narrowing.** Naive design: bi-encoder returns top-500, cross-encoder reranks all 500 → 200ms × 5 = 1 second. Production answer: narrow top-N at stage 1 (top-100 is typical sweet spot per Cohere/published benchmarks) and use the latency-tuned reranker variant (Cohere Fast ~80ms vs Pro ~200ms); if quality requires a heavier reranker, use it only on top-50 and accept the candidate-set narrowing. Alternative: ColBERT as the reranker — late-interaction MaxSim is 2 orders of magnitude faster than a cross-encoder at comparable effectiveness, but the index is 10-100× larger so it doesn't scale as a primary index. For frontier scale, an LLM-as-reranker is sometimes used on top-5 candidates with its own latency SLO; the rerank stage is then a model cascade itself.

3. **Filter-selectivity cliff in multi-tenant search.** Naive pre-filter then ANN: build a candidate set matching the filter, run ANN on the subset — fast when the filter is non-selective, but degrades to brute-force when only 0.1% of vectors match (200-300ms latency spikes). Naive post-filter ANN then filter: ANN returns top-K, filter discards most → may return zero results when the filter is selective enough that no candidates pass. Production answer: in-algorithm filtering (Azure AI Search's ACORN, Lucene ACORN in OpenSearch 3.1+) where the filter predicate is evaluated during HNSW traversal — recall preserved AND query gets faster as filters prune the workload. For multi-tenant with thousands of tenants, Curator-style per-tenant subtree indices embed per-tenant clustering trees inside the global cluster tree (Bloom filters and dynamic shortlists), avoiding both per-tenant-index memory blowup AND the shared-index filter-selectivity cliff.

## Notes for the coach

- **The "1M QPS" headline number is intentionally aggressive.** Most candidates anchor on the headline and over-provision. Reward the candidate who pushes back: "1M QPS in aggregate, or per-query type?" — Perplexity's published 200M queries/day = ~2,300 QPS sustained, so the 1M QPS is likely peak burst or a stress-test number. Sizing for 1M QPS sustained vs 1M QPS burst differs by 10× in capacity.
- **The Anthropic Contextual Retrieval anchor is the highest-leverage stretch move.** A candidate who names it unprompted and prices the prepend-cost via prompt caching demonstrates Anthropic-specific literacy — the kind of "you've read our blog" signal that distinguishes Sr Staff candidates.

If the candidate skips this, surface it as a category-level gap flag ("there's something about the *operational* dimension of this design we haven't touched") rather than naming the specific issue.
- **Out-of-distribution / "I don't know" path is the safety-bar move.** Anthropic specifically grades safety as a first-class architectural concern. A candidate who builds the whole pipeline without ever asking "what if retrieval returns garbage?" is missing the Staff+ safety bar. Surface as a category gap if not addressed.
