# Amazon S3 (distributed object storage at 11-nines durability)

## Bar anchors
- **Mid-level (L4/E4):** Produces a basic object store: PUT writes a blob, GET reads it. Names "replicate the data across multiple nodes" for durability. Discusses metadata (key → location) at category level. Doesn't address strong consistency, multipart upload, erasure coding vs replication, or per-prefix throughput limits unprompted.
- **Senior (L5/E5):** Articulates **metadata vs data plane separation**: metadata index holds (key → location), data plane holds the bytes. Names replication for durability (3 copies typical for HDFS-class). Knows about multipart upload at category level. Discusses eventual vs strong consistency. May or may not address erasure coding or per-prefix throttling.
- **Staff+ (L6/E6+):** Drives proactively. Cites the 11-nines durability target and the "tens of trillions of objects, tens of millions of req/s" scale anchor (Werner Vogels' 2021 published numbers); explicitly notes the "rare-event-happens-multiple-times-per-day" framing — at this scale even 10^-9 events occur many times daily, so retry storms and correlated failures must be designed for. Names the **December 2020 strong-RAW (read-after-write) announcement** explicitly: S3 moved from eventual to strong read-after-write and list-after-write for ALL operations with no performance/cost penalty; the underlying mechanism is a metadata index that serializes writes (data plane can remain eventually consistent because metadata serves as the source of truth on object version). Articulates per-prefix throughput limits: 3500 PUT/POST/DELETE per sec, 5500 GET/HEAD per sec per partitioned prefix; no limit on number of prefixes — practical throughput is fan-out × prefixes. Discusses **erasure coding vs replication economics**: 3× replication = 3× storage cost; Reed-Solomon (e.g., 17-of-30) ≈ 1.76× cost at comparable durability; trade is higher read amplification on degraded read (must read k data shards to reconstruct) and slower repair. Names **multipart upload mechanics**: InitiateMultipartUpload → upload parts in parallel (ETag per part, no ordering required) → CompleteMultipartUpload (atomic publish with list of ETags). Critically: the final POST doesn't need to be issued by the uploader — enables the **magic committer pattern** (Hadoop S3A committers) where distributed jobs achieve job-level atomicity (all workers upload parts; the driver issues the final POST after all complete). Stretch (Sr Staff bar): articulates **lifecycle / tiering** (S3 Standard → IA → Glacier with rehydration latency budgets — Glacier ~12 hours, Glacier Deep Archive 12-48 hours); 5 TiB max object size via multipart; 10,000 max parts per upload; 5 MiB minimum part size except the last.

## Canonical decomposition

### Requirements
**Functional:**
- PUT object (single op or multipart for large objects), GET object, DELETE object, LIST objects with prefix
- Strong read-after-write consistency (since Dec 2020): GET after PUT returns the new version; LIST returns all PUT objects
- Multipart upload: client uploads parts in parallel, then atomically commits via the final POST with list of (part_number, ETag) pairs
- Per-bucket versioning + lifecycle rules (auto-transition to colder tiers, auto-delete after N days, auto-abort incomplete multiparts)
- Server-side encryption (SSE-S3, SSE-KMS, SSE-C) and access control (bucket policies + IAM)
- Cross-region replication (CRR) and same-region replication (SRR)

**Non-functional (with numbers):**
- 11-nines durability (99.999999999%) — losing one object per 10K-objects per 10M years (dominated by correlated failures, not single-disk MTTF)
- 4-nines availability for S3 Standard (99.99%) per published SLA
- 100T+ objects total, tens of millions of requests/sec globally
- Per-prefix throughput: 3500 writes/sec, 5500 reads/sec per partitioned prefix; no cap on prefixes
- Max object size: 5 TiB (multipart upload required for >5 GiB)
- Max parts per upload: 10,000; min part size 5 MiB except last
- Multipart upload TTL: incomplete uploads bill until aborted (lifecycle policy required)

### Core entities
- **Bucket:** top-level namespace; per-bucket settings (versioning, lifecycle, encryption, replication, policy)
- **Object:** (bucket, key) → versioned blob with metadata (size, etag, content-type, custom headers); etag = MD5 hash for single-part, composite for multipart
- **Multipart upload:** upload_id, list of (part_number, etag) accumulated as parts arrive; finalized via CompleteMultipartUpload
- **Metadata index:** strongly-consistent key → object_version mapping; the source of truth on object version (enables strong RAW)
- **Data shards (erasure coded):** Reed-Solomon (k, m) — k data shards + m parity shards; survives up to m losses; rack/AZ-aware placement
- **Lifecycle rule:** declarative policy (transition objects to IA after 30 days, to Glacier after 90 days, abort incomplete multiparts after 7 days)

### API
- `PUT /bucket/key` body=blob, headers=(content-type, x-amz-meta-*) → ETag (for non-multipart objects)
- `GET /bucket/key` → blob with metadata; supports Range header for partial reads
- `DELETE /bucket/key` → soft-delete if versioning enabled (creates delete marker)
- `POST /bucket/key?uploads` → InitiateMultipartUpload → upload_id
- `PUT /bucket/key?partNumber=N&uploadId=U` body=part → ETag for the part
- `POST /bucket/key?uploadId=U` body=list of (part_number, etag) → CompleteMultipartUpload (atomic publish)
- `DELETE /bucket/key?uploadId=U` → AbortMultipartUpload
- `GET /bucket?prefix=P&delimiter=D&marker=M` → ListObjectsV2 (paginated)
- `HEAD /bucket/key` → existence check + metadata without body

### HLD
The architecture cleanly separates **metadata plane** from **data plane**. The **metadata index** is a strongly-consistent distributed KV store mapping `(bucket, key) → object_version_metadata` (size, etag, location-of-shards, content-type, etc); writes to this index are linearizable, serving as the source of truth on which version is current. The **data plane** holds the actual bytes as **erasure-coded shards** distributed across racks/AZs; data-plane writes can be eventually consistent because the metadata index serializes per-key version updates — a GET reads metadata first to find the current version's location, then fetches shards. This separation is the mechanism enabling **strong read-after-write consistency** (announced Dec 2020): once the metadata commit returns, the new version is the canonical one; subsequent reads serialize on the metadata index → see the new version; the data-plane lag (if any) only matters during the metadata-commit critical section, which is small.

**Erasure coding** (e.g., Reed-Solomon (17, 30)): each object's data is split into k=17 data shards + m=13 parity shards (total 30 shards); the object can be reconstructed from any 17 of the 30; survives up to 13 shard losses. Storage cost = 30/17 ≈ 1.76× the raw object size, vs 3× for triple replication, at comparable or better durability. Trade-off: degraded read (any shard missing) requires reading k shards and reconstructing, vs replication where any single replica suffices; repair (re-creating a lost shard) requires reading k surviving shards. Placement: shards spread across racks/AZs so AZ failure loses ≤m shards.

**Multipart upload** mechanics: client calls InitiateMultipartUpload → server returns upload_id; client uploads parts in parallel (each PUT with part_number, server returns ETag; parts can be uploaded out of order, retried independently, and even uploaded by different clients); client calls CompleteMultipartUpload with the list of (part_number, ETag) pairs → server atomically materializes the final object (computing the composite ETag = MD5 of concatenated part-MD5s with the part count). The atomic-publish property enables the **magic committer pattern**: a distributed processing job (Spark, Hive) has all workers upload parts in parallel; the job driver waits for all workers to complete, collects the ETags, then issues the final POST — achieving job-level atomicity (all parts complete or none; partial state never visible to readers). This is the Hadoop S3A magic committer.

**Per-prefix throughput** is the per-partition limit: each partitioned prefix supports 3500 writes/sec and 5500 reads/sec; no limit on number of prefixes per bucket. Practical throughput = aggregate throughput across all hot prefixes. Pre-2018, the prefix hash had to be the first few characters of the key (so e.g. `images/2024-05-24/` keys would all hash to one prefix); since 2018, S3 auto-partitions internally based on observed traffic so applications no longer need hash-prefix-shuffling. Anti-pattern: putting all logs under one date prefix (`logs/2026-05-24/`) at write-heavy workloads; modern best practice: use random prefixes (`<random-hash>/logs/2026-05-24/`) for write-heavy paths or rely on auto-partitioning.

**Lifecycle and tiering**: S3 storage classes form a hierarchy — Standard (hot, ms access) → Standard-IA (infrequent access, ms access, lower storage cost + per-retrieval fee) → Glacier Instant Retrieval (ms access, much lower cost, higher per-retrieval) → Glacier Flexible Retrieval (minutes-to-hours rehydration) → Glacier Deep Archive (12-48h rehydration, cheapest). Lifecycle rules transition objects automatically based on age. Rehydration is the operational headache — surprise bills from a "restore all of Glacier" misconfig.

### Deep dives
1. **Strong read-after-write consistency post-Dec 2020.** Pre-2020, S3 was eventually consistent: a GET immediately after a PUT might return the old version (typically resolved within ms-to-seconds but no upper bound). The Dec 2020 announcement: all S3 GET/PUT/LIST/metadata-operation pairs are now strongly consistent with NO performance or pricing penalty. The published mechanism (inferred from Werner Vogels' post): a metadata index sits in front of the eventually-consistent data plane; writes update the index synchronously (strong consistency on version-current); reads consult the index to find the current version's location, then read from the data plane. Since the index is the source of truth on version, the data plane can remain eventually consistent under the hood — readers serialize on the index, not the data. This is the **classical pattern**: when you need strong consistency on top of an eventually-consistent substrate, add a serializing index above it. Staff+ commit: articulate the metadata-vs-data plane split, address what happens during metadata-index partitions (writes may stall; reads from cached metadata may be stale until reconciled).

2. **Erasure coding economics and degraded-read cost.** Replication: 3× storage cost, 3 reads can serve in parallel (any one suffices), repair is read-1-shard-write-1-shard. Reed-Solomon (k=17, m=13): 1.76× storage cost, comparable durability (survives 13 shard losses), but degraded read requires reading k=17 shards and reconstructing (higher network + compute). Repair (re-creating one lost shard) requires reading k=17 shards across the network. For hot data with high read rate, replication's parallel-read advantage matters; for cold data with low read rate, EC's storage savings dominate. S3 mixes: hot tiers use replication or smaller-k EC; archive tiers (Glacier) use higher-k EC for maximum compression. Trade-off: smaller k = lower storage savings but cheaper repair; larger k = higher savings but more expensive repair. Staff+ commit: pick EC parameters per tier with criteria, address what happens during repair (read amplification on the surviving shards), placement strategy (shards across racks/AZs).

3. **Multipart upload and the magic committer pattern.** Naive distributed write to a single object: multiple workers writing concurrently → race conditions, partial writes, no atomicity. Multipart upload solves this with the InitiateMultipartUpload → upload parts → CompleteMultipartUpload (atomic publish) protocol. The atomicity property is the key: the final POST is the commit point; before it, no reader sees any partial state; after it, the full object is visible. **The final POST doesn't need to be issued by the uploaders** — this enables job-level atomicity for distributed processing: Spark's S3A magic committer has each task upload its output as parts to a "magic" path, then the driver collects the (part_number, ETag) tuples after all tasks complete and issues the final POST. If any task fails, no commit happens → no partial output visible. Trade: orphaned parts (worker crashes after upload but before driver commits) — managed via lifecycle policy "abort incomplete multipart uploads after N days." Staff+ commit: name the magic committer pattern, address orphan cleanup, articulate why the final POST is decoupled from the uploaders (enables distributed-job atomicity).

## Known failure modes
1. **Per-prefix hot-spotting causing throttling.** All objects under one prefix (`logs/2026-05-24/`) at write-heavy load saturate the 3500 writes/sec/prefix cap → HTTP 503 throttling. Production answer: random-prefix sharding (`<hash>/logs/2026-05-24/`) for write-heavy paths; or accept the limit and design downstream batching. Less critical since 2018 (S3 auto-partitions based on traffic) but still recommended for new write-heavy workloads.

2. **Multipart upload billing explosion from abandoned uploads.** Worker crashes mid-upload; parts persist on S3 but no CompleteMultipartUpload happens; orphaned parts continue to bill (storage cost). At high upload rate, orphan accumulation produces surprise bills. Production answer: lifecycle policy with `AbortIncompleteMultipartUpload: DaysAfterInitiation: 7` (or similar); alerting on incomplete-upload count growth; observability dashboard showing per-bucket orphan-storage spend.

3. **Cross-region replication lag breaks strong consistency promises across regions.** Strong RAW is **per-region**; cross-region replication is asynchronous (CRR typically ms-to-seconds, no upper bound under outages). A GET in region B immediately after a PUT in region A may see the old version. Production answer: document the regional consistency model explicitly; for cross-region strong RAW, route reads to write-region (session affinity) for the staleness window; or use S3 Object Lambda + a custom version-validation layer; or accept eventual consistency for cross-region reads.

## Notes for the coach
- **This is the canonical "design object storage" interview prompt.** Asked-confirmed at AWS (canonical), Cloudflare (R2), Backblaze, and any company building object storage. ByteByteGo Vol 2 Ch 9 dedicates a chapter; on every infra interview-prep list.
- **The strong-RAW-since-2020 announcement is the modern-architecture literacy signal.** A candidate proposing eventually-consistent reads from S3 in 2025+ without knowing the 2020 announcement is anchoring on pre-2020 patterns. The Werner Vogels blog post is the primary reference.
- **The magic committer pattern is the L7 distributed-processing flex.** Most candidates think of S3 as a passive blob store; the Staff+ candidate articulates how multipart upload's atomic-publish property enables distributed-job atomicity. Cite the Hadoop S3A committers as the canonical implementation.
- **The 11-nines durability + "rare event happens daily" framing is the operational-reality anchor.** At tens of millions of req/sec, even one-in-a-billion events happen many times per day → design for retry storms, correlated failures, abandoned multipart-uploads.
- **The per-prefix throughput limit (3500 writes / 5500 reads per partitioned prefix) is a concrete operational constant.** Most candidates omit it; surfacing it unprompted is at Sr Staff bar.
- **Cross-coverage:** S3 sits underneath many other primitives — Aurora WAL archival, DynamoDB WAL backup, Kafka tiered storage (KIP-405), Pulsar tiered offload, ML training-checkpoint stores. When other problems mention "archive to S3," this is the substrate. No AI-infra counterpart; the object-store substrate is generic.
- **No `colossus` overlap concern at L6+:** the Colossus filesystem problem (file-system semantics: open/append/close + L4 SSD cache + 1MB chunks) is genuinely distinct from the S3 object-store problem (write-once-read-many + multipart + tiering). If the candidate proposes a filesystem rather than an object store, redirect: "this is the object-store shape — files are immutable after PUT."
